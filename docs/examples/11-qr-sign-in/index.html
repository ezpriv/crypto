Example 11

Sign in on a computer by QR code

On the web version, the user scans a QR code with the phone, confirms, and the computer is signed in with all their data, without typing a password.

In practice Step-by-step flow Code View on GitHub

1In practice

What the user sees. On the web version, the user scans a QR code with the phone, confirms, and the computer is signed in with all their data, without typing a password. Behind that, the computer makes a one-time key pair and secret (newLinkRequest) and opens a channel on the server, which returns a channelId and a receiveToken. The QR code shows the channel, the one-time public key and the secret. The phone seals the user's key pair for that computer (sealForLink), and the server ties the channel to the user and creates a session. The computer receives with its receiveToken, opens the keys (openLink) and checks the public key is the account's.

Why. Typing a long password on a shared or new computer is slow and exposes it to keyloggers. The phone already holds key_A, and the QR code is a channel from screen to camera that the server never sees.

Pros

  • No password typed on the computer. The server never sees the secret, and never sees key_A.
  • Only someone who read the QR code can make a link the computer accepts, so a server can't push its own keys to the computer.
  • A photo of the code can't receive the session or open the keys.
  • The channel works once and the computer checks the public key, so a replayed or swapped link is caught.

Cons and limits

  • Linking trusts whoever shows the QR code. If an attacker gets the user to scan the attacker's code (a phishing page that shows its own QR), the attacker's computer gets key_A (SPEC.md, Limits). The phone must ask the user to confirm, with what the server saw of that browser (type, rough location), and the app's prefix keeps other apps from scanning it for you.
  • The QR code is secret until it's used. A photo of it is enough to forge a link to that computer. Keep channels short-lived.
  • The browser then holds key_A, with the risks of any web copy (05): scripts on the page can read it. Offer "sign out of all browsers".
  • The whole key pair moves. There's no per-device key to revoke. Removing a computer's access means signing it out; it keeps any key it copied.

3Code

The key lines from example/11-qr-sign-in/index.ts. The full file runs every party in one process and ends with node:assert checks.

// computer
const link = ez.newLinkRequest();
const qr = `example-link:1:${channelId}:${toB64url(link.publicKey)}:${toB64url(link.secret)}`;

// phone, after the user confirms
const { channelId, linkPublicKey, linkSecret } = parseQr(qr);
const sealed = ez.sealForLink({ userKeys: ana, channelId, userId: "ana", linkPublicKey, linkSecret });

// computer, after receiving with its receiveToken
const keys = ez.openLink({ sealed, channelId, userId, linkKeys: link });
assert.deepEqual(keys.publicKey, accountPublicKey);

The example-link: prefix is the app's own, so neither another app nor the system camera acts on the code. receiveToken is not in it.
